+++# axislabel-formatter-indexing — implementation plan
+++
+++Requirement: `/workspace/requirements/axislabel-formatter-indexing.yaml`
+++(title: `fix(axis): refactor axisLabel formatter`, category: bugfix; upstream PR mapping
+++`21432.yaml -> axislabel-formatter-indexing.yaml`, see `/workspace/requirements/.rename_map.json`)
+++
+++---
+++
+++## 1. Goal
+++
+++When an axis builds its labels from `axisLabel.customValues`, the user `axisLabel.formatter`
+++callback must be invoked with the **index of the label inside the final, filtered label
+++sequence** (`0, 1, 2, …`), i.e. the position produced by the `map` over the in-extent tick
+++list — *not* `undefined`, and *not* a value looked back up from the tick list (which would
+++collapse repeated values onto the first matching position).
+++
+++Concretely, in `createAxisLabels()` (`/workspace/src/coord/axisTickLabelBuilder.ts`) the
+++`customValues` branch currently calls `labelFormatter(tick)` with **no** second argument, so
+++every user formatter for a `value` / `log` / `time` axis receives `index === undefined`. The
+++fix is to thread the `zrUtil.map` iteration index through to `labelFormatter(tick, index)`,
+++so that:
+++
+++* values filtered out because they are outside `axis.scale.getExtent()` do not consume an
+++  index (the first *rendered* label is index `0`);
+++* the same numeric value appearing more than once yields distinct, increasing indices
+++  (`[1, 3, 3, 7]` -> `0, 1, 2, 3`), instead of every duplicate reporting the first matching
+++  position.
+++
+++Everything else (formatter signatures, `rawLabel`, `tickValue`, tick generation, category
+++axis index semantics, non-custom label generation) must stay byte-for-byte identical.
+++
+++---
+++

+++## 6. Risks / open questions
+++
+++1. **Category axes are intentionally not changed.** For `type: 'category'`,
+++   `makeLabelFormatter` (`/workspace/src/coord/axisHelper.ts:258-272`) ignores the `idx`
+++   argument and passes `tick.value - axis.scale.getExtent()[0]` "for back compatibility", so
+++   `customValues: ['a', 'c', 'a']` still yields indices `0, 2, 0`. The requirement talks about
+++   "the same **numeric** value" and about values "filtered out because they fall outside the
+++   visible axis extent", which is the value/log/time path, and the acceptance signal
+++   explicitly asks for *no* other behaviour change — hence the minimal edit.
+++   *If a category case must also report sequence indices*, the (only) additional edit is in
+++   `/workspace/src/coord/axisHelper.ts`, replacing
+++
+++   ```ts
+++            return function (tick: ScaleTick, idx: number) {
+++                // The original intention of `idx` is "the index of the tick in all ticks".
+++   ```
+++   … body …
+++   ```ts
+++                return (labelFormatter as AxisLabelCategoryFormatter)(
+++                    getAxisRawValue<true>(axis, tick),
+++                    tick.value - axis.scale.getExtent()[0],
+++                    null // Using `null` just for backward compat.
+++                );
+++   ```
+++   with `idx != null ? idx : tick.value - axis.scale.getExtent()[0]`. This was checked to be
+++   safe for the other call site that already passes an index for category axes
+++   (`/workspace/src/coord/cartesian/legacyContainLabel.ts:99`, where
+++   `tick.value === categoryScaleExtent[0] + i`, so `idx` and the ordinal offset are equal),
+++   but it *does* change public behaviour for category `customValues`, so it is deliberately
+++   left out unless required.
+++
+++2. **Time axis.** `tickValuesToNumbers` (`axisTickLabelBuilder.ts:111-121`) duplicates the
+++   first and last value for time axes, so a time axis's formatter indices will be
+++   `0..n+1` with the first two and last two entries sharing a value. That is the intended
+++   "one index per rendered item" semantics, and it is the only user-visible index shift
+++   introduced here. Note that time axis + `customValues` + **function** formatter currently
+++   throws in `/workspace/src/util/time.ts:346` (`tick.time.level` on a `time`-less tick);
+++   that is a separate requirement (`time-axis-customvalues-formatter`) — do not test that
+++   combination here, and expect a textual (not semantic) interaction if both changes land in
+++   the same region later.
+++
+++3. **Estimate vs. determine passes.** `AxisBuilder` formats labels twice per render
+++   (`buildAxisLabel` is called with `AxisTickLabelComputingKind.estimate` and
+++   `.determine`, `/workspace/src/component/axis/AxisBuilder.ts:1332-1352`). Formatters with
+++   side effects therefore see two passes; the new test neutralises this by resetting its
+++   call log right before calling `getViewLabels()`. Do not assert on call counts across a
+++   full render.
+++
+++4. **Index type.** `zrUtil.map`'s callback declares `index?: number`; if a future
+++   `strictNullChecks` is enabled the argument stays assignable to
+++   `makeLabelFormatter`'s `idx?: number`, so no cast is needed now or then.
+++
+++5. Nothing else in the repo reads `formattedLabel` in a way that depends on the index
+++   (`getViewLabels` consumers: `/workspace/src/component/axis/AxisBuilder.ts:1352`,
+++   `/workspace/src/component/axis/AngleAxisView.ts:100`,
+++   `/workspace/src/component/timeline/SliderTimelineView.ts:468`,
+++   `/workspace/src/chart/line/LineView.ts:409`), so the blast radius is limited to the text
+++   produced by user formatters on axes that use `axisLabel.customValues`.

+++> Requirement: `/workspace/requirements/matrix-label-formatter.yaml`
+++> `fix(matrix): fix matrix label formatter does not work`
+++
+++---
+++
+++## 1. Goal
+++
+++`matrix.x.label.formatter`, `matrix.y.label.formatter`, `matrix.body.label.formatter`,
+++`matrix.corner.label.formatter` (and the per-cell overrides
+++`matrix.x/y.data[i].label.formatter`, `matrix.body/corner.data[i].label.formatter`)
+++are currently **completely ignored**. The matrix view always renders the raw cell value.
+++
+++Two concrete defects:
+++
+++1. **Runtime**: `MatrixView#createMatrixCell` builds the label text as `textValue + ''` and hands
+++   it to `setLabelStyle` as `opt.defaultText`, without a `labelFetcher`. `getLabelText()` in
+++   `src/label/labelStyle.ts` only reads `normalModel.get('formatter')` **inside the
+++   `if (labelFetcher)` branch**, so with no fetcher the formatter is never read.
+++2. **Typing**: `MatrixCellStyleOption['label']` is typed as the plain `LabelOption`, which has
+++   **no** `formatter` member at all (it is explicitly commented out in `src/util/types.ts`), so
+++   even declaring a formatter is a TS error for TS users.
+++
+++After the fix:
+++
+++* a **string** formatter is expanded as a simple template (`'{name}'`, `'{value}'`, `'{coord}'` …)
+++  via `formatTplSimple`;
+++* a **function** formatter is invoked and its (non-null) return value is used as the label text;
+++* the callback receives a documented params object:
+++  `{componentType: 'matrix', componentIndex, name, value, coord, $vars}` where `coord` is the
+++  `[xLocator, yLocator]` pair already used for the matrix tooltip (`MatrixXYLocator[]`);
+++* a new public type `MatrixLabelOption` / `MatrixLabelFormatterParams` is exported from
+++  `src/coord/matrix/MatrixModel.ts` and used for `MatrixCellStyleOption['label']`, so the option
+++  is type-checked.
+++
+++---

+++        let text = textValue + '';
+++        _tmpCellLabelModel.option = cellOption ? cellOption.label : null;
+++        _tmpCellLabelModel.parentModel = parentLabelModel;
+++
+++        const formatter = _tmpCellLabelModel.getShallow('formatter');
+++        if (formatter) {
+++            const params = {
+++                componentType: 'matrix' as const,
+++                componentIndex: matrixModel.componentIndex,
+++                name: text,
+++                value: textValue as unknown,
+++                coord: xyLocator.slice() as MatrixXYLocator[],
+++                $vars: ['name', 'value', 'coord'] as const
+++            };
+++            if (isString(formatter)) {
+++                text = formatTplSimple(formatter, params);
+++            }
+++            else if (isFunction(formatter)) {
+++                const formattedText = formatter(params);
+++                if (formattedText != null) {
+++                    text = formattedText + '';
+++                }
+++            }
+++        }
+++
+++        setLabelStyle(
+++```
+++
+++Why this works / rationale:
+++
+++* `_tmpCellLabelModel` is `new Model<MatrixCellStyleOption['label']>()`
+++  (`MatrixView.ts:355`); after Edit 2 that is `MatrixLabelOption`, so `getShallow('formatter')`
+++  type-checks and returns `string | ((params: MatrixLabelFormatterParams) => string)`.
+++* `Model#getShallow` (`/workspace/src/model/Model.ts:120-135`) falls back to `parentModel` when
+++  the own option misses the key. Since `_tmpCellLabelModel.option` is the *per-cell*
+++  `data[i].label` and `_tmpCellLabelModel.parentModel` is the dimension/body/corner-level
+++  `label` model, the existing two-level cascade documented at `MatrixModel.ts:185-189` is
+++  respected for free (cell-level formatter overrides the dim/body/corner one).
+++* `text` is fed both to `setLabelStyle({defaultText: text, ...})` **and** to
+++  `setTooltipConfig({itemName: text, ...})` further down (line 321-329), so the tooltip /
+++  overflow tooltip shows the formatted text too — which is the desired behaviour, since the
+++  tooltip exists mainly to reveal truncated label text.
+++* `formattedText != null` guard: a function formatter returning `undefined` keeps the raw value
+++  instead of rendering the string `"undefined"`.
+++* Everything is inside `if (textValue != null)`, i.e. the formatter is not invoked for empty
+++  cells; that matches the pre-existing "no text ⇒ no `Text` element" behaviour and avoids
+++  creating labels for the (very numerous) empty body cells.
+++* `tsconfig.json` has no `strict`/`strictNullChecks`, so `MatrixCellStyleOption['label']`
+++  collapses to `MatrixLabelOption` and `keyof` works normally.
+++* The inferred type of the `params` const is an anonymous object type, hence it gets an implicit
+++  index signature and is assignable to `formatTplSimple`'s `param: Dictionary<any>`.

+++## 6. Risks / open questions
+++
+++1. **`formatTplSimple` replaces only the first occurrence** of each `{key}` (it uses
+++   `String#replace` with a string pattern). `'{name}-{name}'` yields `'A-{name}'`. This matches
+++   the existing behaviour of `calendar.dayLabel/monthLabel/yearLabel.formatter`, so it is
+++   consistent with the rest of ECharts — but it is a known limitation worth noting in docs.
+++2. **`{componentType}`, `{componentIndex}`, `{coord}`, `{$vars}` are also substitutable** by
+++   `formatTplSimple` because it iterates every key of the params object. `{coord}` stringifies
+++   the array as `0,-1`. Harmless, but it means the template namespace is slightly larger than
+++   `name`/`value`.
+++3. **The formatted text also becomes the tooltip `itemName`** (`setTooltipConfig({itemName: text})`
+++   at `MatrixView.ts:324`), because `text` is reused. That is intentional (the matrix tooltip is
+++   primarily an overflow-reveal mechanism), but it is a behaviour change for users who declare a
+++   label formatter *and* rely on `matrix.tooltip.formatter(params.name)` returning the raw value.
+++   If that is undesirable, capture `const rawText = textValue + '';` before formatting and pass
+++   `rawText` to `setTooltipConfig`. The upstream fix does **not** do this — it reuses `text`.
+++4. **`getShallow` parent fallback**: `_tmpCellLabelModel.parentModel` is the dim/body/corner
+++   `label` model, whose own `parentModel` is the dim/body/corner model. A user writing
+++   `matrix.x.formatter` (not under `label`) would therefore accidentally take effect. This mirrors
+++   the existing behaviour of `_tmpCellLabelModel.get('silent')` at `MatrixView.ts:334`, so no new
+++   class of problem is introduced.
+++5. **Not covered**: the label of *series* drawn inside the matrix (heatmap/scatter labels) — those
+++   go through the normal series label pipeline and already work. Only matrix component cell
+++   labels are touched.
+++6. **`emphasis`/`blur`/`select` label states** are still unsupported by matrix cells (see the
+++   `// Currently do not support other states` comment at `MatrixView.ts:291`), so the formatter is
+++   applied to the normal state only. Consistent with the current design.
+++7. **Rich text** (`label.rich` + `{a|...}` markup) combined with a string formatter: the template
+++   substitution happens before `setLabelStyle`, so rich tags in the formatter output still work as
+++   usual; but a rich tag such as `{styleName|text}` inside the formatter string is *not* a
+++   `formatTplSimple` key so it passes through untouched. Verified by reading `formatTplSimple`,
+++   not by running a rich-text case — worth a manual smoke test if rich matrix labels matter.

+++# radar-clockwise-option — Implementation Plan
+++
+++## 1. Goal
+++
+++Add a new `radar.clockwise` component option (boolean) to the **radar coordinate system**, so that the
+++order in which indicator axes are laid out around the circle can be reversed.
+++
+++Engineering statement:
+++
+++* `RadarOption` (`src/coord/radar/RadarModel.ts`) gains `clockwise?: boolean`, defaulting to `false`.
+++* `Radar` (`src/coord/radar/Radar.ts`) gains a public `clockwise: boolean` field (sibling of the
+++  existing `startAngle`, `cx`, `cy`, `r`, `r0` fields), read in `Radar.prototype.resize()`.
+++* The per-indicator angle computation in `Radar.prototype.resize()` changes from a fixed
+++  `+idx * 2π / n` step to a signed `dirSign * idx * 2π / n` step, where `dirSign === -1` when
+++  `clockwise` is truthy (because `coordToPoint()` uses `y = cy - coord * sin(angle)`, i.e. *increasing*
+++  angle already means *counter-clockwise* on screen).
+++* The stale `// TODO clockwise` marker at the top of `src/coord/radar/Radar.ts` is removed.
+++* Indicator 0 must stay exactly at `startAngle` in both directions (no regression for existing charts,
+++  since the default `false` reproduces today's math bit-for-bit: `dirSign === 1`).
+++* Nothing in `src/component/radar/RadarView.ts` needs to change — see Findings §2.4 for the proof that
+++  label / axis-name placement is preserved.
+++

+++
+++`/workspace/src/coord/radar/Radar.ts:125-150` (`resize()`), verbatim:
+++
+++```ts
+++    resize(radarModel: RadarModel, api: ExtensionAPI) {
+++        const refContainer = createBoxLayoutReference(radarModel, api).refContainer;
+++
+++        const center = radarModel.get('center');
+++        const viewSize = Math.min(refContainer.width, refContainer.height) / 2;
+++        this.cx = numberUtil.parsePercent(center[0], refContainer.width) + refContainer.x;
+++        this.cy = numberUtil.parsePercent(center[1], refContainer.height) + refContainer.y;
+++
+++        this.startAngle = radarModel.get('startAngle') * Math.PI / 180;
+++
+++        // radius may be single value like `20`, `'80%'`, or array like `[10, '80%']`
+++        let radius = radarModel.get('radius');
+++        if (isString(radius) || isNumber(radius)) {
+++            radius = [0, radius];
+++        }
+++        this.r0 = numberUtil.parsePercent(radius[0], viewSize);
+++        this.r = numberUtil.parsePercent(radius[1], viewSize);
+++
+++        each(this._indicatorAxes, function (indicatorAxis, idx) {
+++            indicatorAxis.setExtent(this.r0, this.r);
+++            let angle = (this.startAngle + idx * Math.PI * 2 / this._indicatorAxes.length);
+++            // Normalize to [-PI, PI]
+++            angle = Math.atan2(Math.sin(angle), Math.cos(angle));
+++            indicatorAxis.angle = angle;
+++        }, this);
+++    }
+++```
+++
+++`idx * Math.PI * 2 / n` is always added, so indicator index always advances counter-clockwise on
+++screen. There is no way to flip it.
+++
+++Screen-direction proof — `/workspace/src/coord/radar/Radar.ts:90-96`:
+++
+++```ts
+++    coordToPoint(coord: number, indicatorIndex: number) {
+++        const indicatorAxis = this._indicatorAxes[indicatorIndex];
+++        const angle = indicatorAxis.angle;
+++        const x = this.cx + coord * Math.cos(angle);
+++        const y = this.cy - coord * Math.sin(angle);
+++        return [x, y];
+++    }
+++```
+++
+++`y` is negated, so a *larger* angle moves the point counter-clockwise in screen space. Hence
+++`clockwise: true` ⇒ step sign `-1`.

+++## 6. Risks / open questions
+++
+++1. **Default value.** I chose `clockwise: false` so that every existing radar chart renders
+++   identically (the requirement says the change must not break "the rest of the radar rendering
+++   contract"). Every other ECharts component that has `clockwise` defaults it to `true`
+++   (`src/component/polar/install.ts:43`, `src/chart/pie/PieSeries.ts:220`,
+++   `src/chart/gauge/GaugeSeries.ts:209`, `src/chart/sunburst/SunburstSeries.ts:227`,
+++   `src/chart/chord/ChordSeries.ts:308`), so there is a naming-consistency argument for `true`. If the
+++   upstream decision was `true`, the *only* change needed is the literal in Edit 6 (plus the doc
+++   comments and the two "default" assertions in the spec) — the mechanism is identical.
+++2. **`pointToData` nearest-axis search.** `/workspace/src/coord/radar/Radar.ts:98-123` uses
+++   `Math.abs(radian - indicatorAxis.angle)` without wrap-around handling, so an axis at `+π` and a
+++   pointer at `-π` are considered maximally far apart. This is a pre-existing bug, direction-agnostic,
+++   and deliberately left untouched to keep the change minimal. It is worth flagging in review.
+++3. **Split-area winding.** `_buildSplitLineAndArea` (`src/component/radar/RadarView.ts:129-165`)
+++   produces ring polygons whose winding flips with `clockwise`. Canvas/SVG fill for the
+++   outer-forward/inner-reversed pair is winding-symmetric, so no visual change is expected, but the
+++   `shape: 'polygon'` + `splitArea` case is the one to eyeball in the visual test.
+++4. **`radar.axisName.formatter` / `triggerEvent`.** Both are keyed off the indicator model, not the
+++   angle, so they follow the reordered axes automatically. No action.
+++5. **Docs.** The option reference lives in the separate `apache/echarts-doc` repository; adding
+++   `radar.clockwise` there is out of scope for this repo but should be filed as a follow-up.
+++6. **`echarts.util.merge` in the visual test — verified available.** `src/export/api.ts:54` does
+++   `export * as util from './api/util'`, and `src/export/api/util.ts:20-23` re-exports
+++   `extend, defaults, clone, merge`. `src/export/core.ts` does `export * from './api'`, so
+++   `echarts.util.merge(target, source, true)` is on the public surface. No fallback needed.

+++        const chunks = this._chunks;
+++
+++        for (let i = 0, len = this.count(); i < len; i++) {

+++# toolbox-emphasis-color — implementation plan
+++
+++## 1. Goal
+++
+++`ToolboxModel.defaultOption` currently declares the *same* colour token for the normal icon
+++stroke and for the emphasis (hover / active) icon stroke:
+++
+++* `iconStyle.borderColor` → `tokens.color.accent50`
+++* `emphasis.iconStyle.borderColor` → `tokens.color.accent50`
+++
+++Because `ToolboxView` maps `borderColor` → `style.stroke` for both the normal style and the
+++`'emphasis'` element state, hovering a toolbox icon (or an icon being switched into the
+++`emphasis` icon status by `dataZoom` / `brush` / `magicType`) produces **no visible change** —
+++the emphasis state paints exactly the same stroke colour as the normal state.
+++
+++Engineering change: give the toolbox emphasis state a *darker*, clearly distinct accent token
+++(`tokens.color.accent70`, `#404c76`) so `emphasis.iconStyle.borderColor` differs from
+++`iconStyle.borderColor` (`tokens.color.accent50`, `#6578ba`). This is a one-line default-option
+++change; no view/render logic needs to change because the plumbing already works.
