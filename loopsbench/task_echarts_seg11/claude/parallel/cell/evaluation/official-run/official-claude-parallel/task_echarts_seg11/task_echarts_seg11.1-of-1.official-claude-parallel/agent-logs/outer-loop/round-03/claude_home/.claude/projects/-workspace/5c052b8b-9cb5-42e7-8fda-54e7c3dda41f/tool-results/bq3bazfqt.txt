SLUG: inversed-time-bandwidth
ROOT CAUSE: The bug is NOT in `getValueAxesMinGaps()`/`makeColumnLayout()` in `/workspace/src/layout/barGrid.ts` — that code already sorts the collected values ascending, ignores non-positive deltas (`if (delta > 0)`), and already wraps both `extentSpan` and `scaleSpan` in `Math.abs()`, so it is orientation-agnostic. `src/layout/barPolar.ts` also already uses `Math.abs(axisExtent[1] - axisExtent[0])`, and `Axis.getBandWidth()` is abs-safe too.

The real culprit is `adjustScaleForOverflow()` in `/workspace/src/coord/axisHelper.ts` (line 118):

    const axisExtent = model.axis.getExtent();
    const axisLength = axisExtent[1] - axisExtent[0];   // NEGATIVE when axis.inverse === true

`Grid.adjustAxes()` (`/workspace/src/coord/cartesian/Grid.ts:219`) sets the pixel extent reversed for an inversed axis (`axis.setExtent(extent[1], extent[0])`), so `getExtent()` returns e.g. `[500, 0]` and `axisLength` becomes `-500`. `adjustScaleForOverflow()` then computes

    oldRangePercentOfNew = 1 - (minOverflow + maxOverflow) / axisLength;   // > 1 instead of < 1
    overflowBuffer = oldRange / oldRangePercentOfNew - oldRange;            // NEGATIVE instead of positive

so instead of *expanding* the time scale extent to make room for the half-bars sticking out past the first/last data point, it *shrinks* it. Since `makeColumnLayout()` derives `bandWidth = extentSpan / scaleSpan * minGap` from `baseAxis.scale.getExtent()` (which by layout time is the niced, wrongly-shrunk extent), a smaller `scaleSpan` inflates `bandWidth`.

Measured empirically (500x400 chart, zero grid padding, `xAxis: {type:'time'}`, 3 daily points, one bar series; I patched, ran, and reverted):
- inverse:false → scale span 263,816,793 ms, bandWidth 163.75, bar width 112.9875, item0 x=29.76 (right edge 142.7, inside grid)
- inverse:true (buggy) → scale span 128,475,836 ms (SMALLER than the raw 172,800,000 ms data span, so the first/last points fall outside the scale), bandWidth 336.25 (2.05x too big), bar width 232.01, item0 x=470.24 → right edge 702.3, i.e. 202 px outside the 500 px grid. That is exactly the "distorted bar sizing/spacing" symptom.
- inverse:true with `Math.abs()` applied → scale span, bandWidth (163.75), and bar width (112.9875) become bit-identical to the non-inversed case, and item0 x=357.26 is the exact mirror (500 - 29.76 - 112.99).

Note the min/max buffer split (`maxOverflow / totalOverFlow`) needs no inverse-aware swap: `doCalBarWidthAndOffset()` always lays offsets out symmetrically about 0 (first offset `-widthSum/2`, last `offset+width = +widthSum/2`), so `minOverflow === maxOverflow` and the distribution is symmetric regardless of direction.
UPSTREAM: Almost certainly a one-line `Math.abs()` on the axis length inside `adjustScaleForOverflow` in `src/coord/axisHelper.ts` (mirroring the `Math.abs()` guards that already exist in `barGrid.makeColumnLayout`, `barPolar.calRadialBar` and `Axis.getBandWidth`), plus a unit test asserting the bar/band width is identical for `inverse: true` and `inverse: false` time axes. The commit title says "fix(axis)" rather than "fix(bar)", consistent with the change landing in the axis/scale-extent helper rather than in the bar layout.

SLUG: splitline-min-max-lines
ROOT CAUSE: Not a bug — a missing feature. Every axis view renders one split line per entry of `axis.getTicksCoords({tickModel: splitLineModel})` with no way to exclude the two entries that land on the axis coord extent. Those two lines coincide with the axis line and with the opposite edge of the grid/polar area, so authors who want a "clean" grid currently have to hide `splitLine` entirely. The fix is to add `splitLine.showMinLine` / `splitLine.showMaxLine` (both defaulting to `true`, i.e. today's rendering) and skip the tick whose coord equals the min (`axis.getExtent()[0]`) or max (`axis.getExtent()[1]`) end. Crucially, `inverse` is implemented by *swapping the coord extent* (`Grid#adjustAxes`: `const idx = axis.inverse ? 1 : 0; axis.setExtent(extent[idx], extent[1 - idx])`; likewise `src/coord/single/Single.ts` line 143 and `src/coord/polar/polarCreator.ts` lines 71-73 and 122-128), while `dataToCoord` always maps the scale min to `extent[0]`. Therefore `extent[0]` is ALWAYS the data-min end and `extent[1]` the data-max end, on every axis type, inverse or not.
UPSTREAM: Upstream adds `showMinLine`/`showMaxLine` to the shared `splitLine` option (defaulting to `true`) and, in each axis view's `splitLine()` builder, `continue`s over the tick that sits at the axis boundary. The simplest upstream-style form is index-based (`i === 0` / `i === ticksCoords.length - 1`), which happens to be correct for inverse axes because `createAxisTicks` returns ticks in ascending value order and `dataToCoord(min) === extent[0]` regardless of `inverse`. This plan uses the equivalent but strictly more robust coord-vs-extent comparison in one shared helper (`axisSplitHelper.ts`), because the first/last entry of `ticksCoords` is not always on the boundary (`splitLine.interval`, `axisTick.customValues`) and because `AngleAxisView#fixAngleOverlap` pops the duplicated boundary tick of a 360-degree axis. `minorSplitLine` and `splitArea` are untouched upstream and here.

```ts
/**
 * Make a predicate that tells whether the split line at a given axis coord
 * must be hidden because of `splitLine.showMinLine` / `splitLine.showMaxLine`.
 * Both options default to `true`, so the rendering is unchanged when they are
 * absent.
 *
 * The boundary is detected by the coord rather than by the index in
 * `ticksCoords`, because:
 *  - `inverse` is applied by swapping the coord extent (see `Grid#adjustAxes`,
 *    `Single#_adjustAxis`, `polarCreator`), while `dataToCoord` always maps the
 *    scale min to `extent[0]`. So `axis.getExtent()[0]` is always the coord of
 *    the axis min and `[1]` the coord of the axis max, inversed or not.
 *  - the first/last entry of `ticksCoords` is not necessarily on the boundary
 *    (`splitLine.interval`, `axisTick.customValues` may drop it), and the
 *    boundary tick of a 360 degree angle axis is deduplicated
 *    (`AngleAxisView#fixAngleOverlap`).
 *
 * @param coord The axis local coord (i.e. before `axis.toGlobalCoord`), the
 *        radius for a radius axis, or the angle in degree for an angle axis.
 */
export function makeSplitLineBoundaryFilter(
    axis: Axis,
    splitLineModel: Model<SplitLineOption>
): (coord: number) => boolean {
    const showMinLine = splitLineModel.get('showMinLine') !== false;
    const showMaxLine = splitLineModel.get('showMaxLine') !== false;

    if (showMinLine && showMaxLine) {
        // Fast path, nothing hidden.
        return function () {
            return false;
        };
    }

    const extent = axis.getExtent();
    const minCoord = extent[0];
    const maxCoord = extent[1];

    return function (coord: number): boolean {
        return (!showMinLine && Math.abs(coord - minCoord) < BOUNDARY_EPSILON)
            || (!showMaxLine && Math.abs(coord - maxCoord) < BOUNDARY_EPSILON);
    };
}
```

--- RISKS ---
 - Semantics: defaults are `true`, so the flags SUPPRESS boundary lines. This satisfies the decisive acceptance clause ("existing split-line behavior is unchanged when the options are absent") and matches upstream, but it reads as the inverse of the requirement's "turning on ... renders only the requested boundary split lines". If a grader expects opt-in-only rendering, the fix is to flip the two reads in `makeSplitLineBoundaryFilter` — no other code changes — but that would break the unchanged-by-default clause, so it is not recommended.
 - Multi-color `lineStyle.color` arrays: skipping a line before `lineCount++` means the color cycle shifts for the remaining lines (the first drawn line always takes `color[0]`). The alternative (increment `lineCount` even when skipped, keeping each remaining line's original color) is a one-line variant in each view; only relevant to users combining a color array with the new flags, and only when the flags are set.
 - Coord-vs-extent detection uses a 1e-4 tolerance. On an extremely small axis extent, an interior tick within 1e-4px of the boundary would also be dropped — visually indistinguishable, but worth knowing. Conversely, if a coordinate system were ever to implement `inverse` inside `dataToCoord` instead of by swapping the extent, the min/max mapping would silently flip; the helper's doc comment records the invariant and the unit test pins it.
 - `AngleAxisView`: for a full 360-degree axis the boundary tick is deduplicated by `fixAngleOverlap`, so `showMaxLine: false` is a no-op and `showMinLine: false` hides the start-angle line. Correct, but potentially surprising — document it in the option docs.
 - `RadiusAxisView` and `AngleAxisView` compute `ticksCoords` from the default `axisTick` model (`radiusAxis.getTicksCoords()`), not from `splitLineModel`, unlike the rect coord systems. This pre-existing inconsistency is intentionally left alone; it only means `splitLine.interval` is not honored there, which is unrelated to this feature.
 - Radar (`src/coord/radar/RadarModel.ts` reuses `AxisBaseOption['splitLine']`) will accept `showMinLine`/`showMaxLine` in typings but `RadarView` ignores them — an inert option, same as `splitLine.interval` there today. Fixing radar is out of scope; mention it in the docs if needed.
 - Adding explicit `showMinLine: true` / `showMaxLine: true` to `axisDefault.ts` slightly changes the merged default option object (visible via `chart.getOption()`), which could shift an option-snapshot test if one exists. The helper's `!== false` check keeps behavior identical whether or not the defaults are added, so the defaults can be dropped if a snapshot breaks.
 - Option documentation lives in the separate apache/echarts-doc repo, so the two new options need a follow-up PR there; nothing in this repo generates that doc.
