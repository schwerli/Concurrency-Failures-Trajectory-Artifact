########## Raw output mechanics: byte-level framing, stream routing, encoding, env-insensitivity, broken-pipe, repr/JSON escaping, and int() parsing internals
  [1] LINE FRAMING: On success the program writes exactly 12 lines to stdout, each terminated by exactly one LF (0x0A). There is NO trailing blank line, no CR anywhere (0 matches for \r in od -c), and no BOM or preamble (first byte of stdout is '{'). Canonical case --a Q --b 1 --c 2 => 900 bytes total; per-line lengths excluding LF are 67,60,18,72,63,40,52,19,159,119,112,107 which sum to 888, +12 LF = 900 exactly. Emit with a plain print()-equivalent (write text + '\n') and no final extra newline.
  [2] STREAM ROUTING: All 12 lines go to stdout; stderr receives exactly 0 bytes on every successful run (verified `2>/dev/null | wc -c` = 900 and `1>/dev/null | wc -c` = 0). --help writes 128 bytes to stdout, 0 to stderr, exit 0. argparse errors write 0 bytes to stdout and go entirely to stderr with exit 2. Never interleave anything onto stderr on the success path.
  [3] OUTPUT ENCODING IS ALWAYS UTF-8 AND IS NOT ENVIRONMENT-CONFIGURABLE. The frozen build ignores Python env config entirely: LC_ALL=C, LANG=C, LC_ALL=POSIX, PYTHONUTF8=0, PYTHONIOENCODING=ascii, PYTHONIOENCODING=latin-1, and even PYTHONIOENCODING=bogus_codec_xyz all produce byte-identical output and exit 0 (a bogus codec would abort a normal CPython, proving env is ignored). For the port: hardcode UTF-8 stdout; do not read locale/encoding env vars.
  [4] NON-ASCII SPLIT BEHAVIOUR: dict-repr lines (1,3,4,6,8,9,10,11,12) emit non-ASCII as RAW UTF-8 bytes (U+00FC -> 303 274; U+1F600 -> 360 237 230 200). Delta lines (2,5,7) emit them as ASCII \uXXXX escapes, astral as UTF-16 surrogate pairs (U+1F600 -> 😀). Both on the same run.
  [5] PYTHON repr() STRING RULES for the dict-repr lines: choose delimiter = single quote, UNLESS the string contains a single quote and no double quote, in which case use double quotes. Verified: "it's" -> "it's" (double-quoted, unescaped); 'say "hi"' -> 'say "hi"' (single-quoted, unescaped); `both'and"q` -> 'both\'and"q' (single-quoted, only the apostrophe escaped). Backslash -> \\. This is also why DeepDiff path keys always print double-quoted: the key text root['x'] contains an apostrophe.
  [6] PYTHON repr() CONTROL-CHAR ESCAPES (dict-repr lines): \t -> \t, \n -> \n, \r -> \r, and other C0/DEL use lowercase 2-hex \xNN: 0x01 -> \x01, 0x0B -> \x0b, 0x1B -> \x1b, 0x7F -> \x7f. Delta/json.dumps instead uses \uXXXX 4-hex lowercase for the same chars: , , ,  (but \t and \n stay as short \t/\n, and " -> \", \ -> \\).
  [7] INVALID UTF-8 IN argv NEVER ERRORS. A raw 0xFF in --a is decoded via surrogateescape to lone surrogate U+DCFF; repr renders it as the 7 ASCII chars '\udcff' and json.dumps as \udcff, so nothing un-encodable ever reaches stdout. Result: exit 0, 12 lines, 985 bytes. Note repr uses \uXXXX (not \xNN) for surrogates.
  [8] NUL BYTE IN --a IS IMPOSSIBLE, not merely unsupported: execve argv elements are NUL-terminated C strings. bash reports 'warning: command substitution: ignored null byte in input' and the program receives 'AB'. No port behaviour needed.
  [9] BROKEN PIPE (stdout closed early): if total output exceeds the ~64 KiB pipe buffer, the program dies with exit code 1 and writes a Python traceback to stderr ending in `BrokenPipeError: [Errno 32] Broken pipe` followed by `[PYI-<PID>:ERROR] Failed to execute script 'test15' due to unhandled exception!` (the PYI number is the PID and varies run to run).   [10] TRACEBACK SOURCE-LINE IS A CWD ARTIFACT, NOT PACKED DATA: run from /workspace/dataset (which contains test15.py) the traceback includes the source text line `    print(result1)`; run from /tmp/nocwd it prints only `  File "test15.py", line 21, in <module>` with no source line. linecache is resolving test15.py relative to cwd.   [12] EMPTY-DIFF EDGE CASES the port must handle: an empty DeepDiff prints exactly `{}` and its Delta prints exactly `<Delta: {}>`.   [15] INT PARSING MECHANISM (both --b and --c). Python first runs _PyUnicode_TransformDecimalAndSpaceToASCII, then a C-locale ASCII parse. Verified 0x1C -> exit 2 `invalid int value: '\x1c42'`, 0x1D -> reject. 0x7F DEL -> reject. But 0x09/0x0A/0x0B/0x0C/0x0D/0x20 wrapping IS accepted.
  [17] CONSEQUENCE FOR >=127 WHITESPACE: accepted (mapped to space) for U+0085 NEL, U+00A0 NBSP, U+1680 OGHAM, U+2007 FIGURE SPACE, U+2028 LINE SEP, U+2029 PARA SEP, U+202F NARROW NBSP, U+205F MEDIUM MATH SPACE, U+3000 IDEOGRAPHIC SPACE.   [18] CONSEQUENCE FOR UNICODE DIGITS: --b/--c accept any Nd decimal digits and normalise them. ########## The extra 'diff' key inside values_changed for multi-line strings (deepdiff `_diff_str` + `difflib.unified_diff`)
  [1] WHERE IT CAN APPEAR: the 'diff' key only ever appears inside a `values_changed` entry whose two values are `str`. In this program that is only `root['x']` (args.a vs args.a*2), i.e. only on printed lines 4, 9, 10 and 11. It NEVER appears for `root['y']` (ints - confirmed with 20-digit ints on lines 1, 9, 10, 12) and NEVER for `dictionary_item_added`. Lines 1, 6, 12 never have it because x is unchanged there.
  [2] TRIGGER: add the 'diff' key iff the string contains an ASCII LF (U+000A). It is NOT `splitlines()`-based. Negative (no 'diff' key, verified individually): CR `\r`, VT `\x0b`, FF `\x0c`, FS `\x1c`, GS `\x1d`, RS `\x1e`, NEL U+0085 (C2 85), LS U+2028, PS U+2029, TAB, and a literal backslash+n. Positive: `\n` and `\r\n`. A trailing-only newline (`--a $'x\n'`) DOES trigger. Implementable rule for this program: `'\n' in args.a`.
  [3] SPLITTING: once triggered, lines come from Python `str.splitlines()` (full semantics: breaks on \n \r \r\n \v \f \x1c \x1d \x1e \x85    , and no trailing empty element after a final break) - NOT `split('\n')`. Two discriminators: (a) `--a $'a\r\nb'` yields diff body lines `a` and `b` with the `\r` GONE; (b) `--a $'a\nb\n'` yields header `@@ -1,2 +1,4 @@` whereas split('\n') would give `@@ -1,3 +1,5 @@` plus a trailing empty context line.
  [4] KEY ORDER: always exactly `new_value`, `old_value`, `diff` - 'diff' is always the last key of the entry (it is added by `dict.update` after the base dict is built). Verified on lines 4, 9, 10, 11 in both directions.
  [5] FORMAT: `entry['diff'] = '\n'.join(difflib.unified_diff(old.splitlines(), new.splitlines(), lineterm=''))` with defaults fromfile='', tofile='', n=3. Guarded by `if diff:` (non-empty list).
  [6] HEADERS: the first two joined elements are exactly `'--- '` and `'+++ '` - four characters each, trailing space PRESERVED, no tab/date suffix. Byte-verified with od: `'   -   -   -       \   n   +   +   +       \   n` i.e. `--- ` LF `+++ ` LF inside the string.
  [7] HUNK HEADER: `'@@ -{r1} +{r2} @@'` (one space after `@@`, one space between ranges, one space before the closing `@@`).   [8] BODY: `' ' + line` for equal, `'-' + line` for old lines of delete/replace, `'+' + line` for new lines of insert/replace; within a `replace` all `-` lines precede all `+` lines. The joined string never ends with a newline, and there is never a `\ No newline at end of file` marker.

########## Python int() acceptance rules for --b/--c, and the exact error message for rejects
  [1] TWO-LAYER MODEL. A value for --b/--c passes through two independent gates: (1) argparse's option-lookalike pre-filter, which only applies to the space-separated form `--b VAL` and can reject before int() ever runs; (2) CPython's `int(str)` parser. Use the `--b=VAL` form to bypass gate (1) entirely and test gate (2) in isolation. Implement both.
  [2] GATE 1 (argparse option-lookalike, space-separated form ONLY). Given `--b VAL`: if VAL starts with '-' AND VAL != '-' AND VAL does NOT match the regex `^-\d+$|^-\d*\.\d+$` (where `\d` is Unicode-aware, i.e. matches any Nd codepoint) AND VAL contains no ASCII space character U+0020, then argparse classifies VAL as an option string, consumes no argument, and fails with `expected one argument` (int() is never called). Otherwise VAL is passed to int(). Verified rejects: '-0x10', '-1_0', '-abc', '-5x', '-1e3', '--5'. Verified passed-through: '-5', '-12', '-٥' (match negative regex), '-5 ' and '- 5' (contain a space), ' -5' (does not start with '-'), '-5.0' (matches the float branch, then int() rejects it).
  [3] GATE 2 STEP A (Unicode-to-ASCII transform, equivalent to CPython `_PyUnicode_TransformDecimalAndSpaceToASCII`). Map the input string s codepoint-by-codepoint to a new string t: if cp < 0x80, copy verbatim; else if cp is in the NON-ASCII SPACE SET, emit ' ' (U+0020); else if cp has Unicode general category Nd, emit the ASCII digit for its decimal value ('0'-'9'); else REJECT immediately. Astral-plane Nd digits are handled and each counts as ONE codepoint (verified U+1D7CE, U+1D7D8, U+1D7F6, U+104A0, U+10D30, U+1E950, U+11066, U+1FBF5 all accepted).
  [4] GATE 2 NON-ASCII SPACE SET is exactly: U+0085, U+00A0, U+1680, U+2000..U+200A, U+2028, U+2029, U+202F, U+205F, U+3000. Verified closed by testing immediate neighbours: U+0084 reject / U+0085 accept / U+0086 reject; U+167F reject / U+1680 accept / U+1681 reject; U+1FFF reject / U+2000..U+200A accept / U+200B reject; U+202E reject / U+202F accept / U+2030 reject; U+205E reject / U+205F accept / U+2060 reject; U+2FFF reject / U+3000 accept / U+3001 reject. Also rejected: U+180E, U+FEFF, U+3164, U+009F.
  [5] GATE 2 STEP B (ASCII grammar on the transformed string t). Accept iff t fully matches `^[\t\n\x0b\x0c\r ]*[+-]?[0-9](?:_[0-9]|[0-9])*[\t\n\x0b\x0c\r ]*$` — i.e. optional surrounding ASCII whitespace, optional single leading '+' or '-', then one or more digits with single underscores allowed only BETWEEN digits. Leading zeros are allowed and ignored. Verified rejects: '' , ' ', '-', '+', '_1', '1_', '1__0', '+_5', '_+5', '5+', '+-5', '- 5', '5 5', '5.0', '5e3', '1e0', '5.', '.5', '0x10', '0X10', '0b1', '0o7', '1j', 'inf', 'nan', 'None', 'Infinity', 'true', '5-', '--5'. Verified accepts: '5', '+5', '-5', '007', '-0', '0', '1_000', '1_0_0', '+1_0', '-1_0', '-1_000', '-007', '1_000_000'.
  [6] GATE 2 ASCII WHITESPACE SET is exactly {0x09 TAB, 0x0A LF, 0x0B VT, 0x0C FF, 0x0D CR, 0x20 SPACE} — the C `Py_ISSPACE` set, NOT `str.isspace()`. COUNTEREXAMPLE TO THE BRIEF: U+001C, U+001D, U+001E, U+001F all have `str.isspace() == True` in Python but are REJECTED here, because they are ASCII so Step A copies them verbatim and Step B's ASCII tokenizer does not treat them as whitespace. Observed: `--b=$'\x1c5\x1c'` -> `invalid int value: '\x1c5\x1c'`. Non-ASCII spaces such as U+0085 and U+00A0 ARE accepted precisely because Step A rewrites them to ' '. Also verified rejects: 0x08, 0x0E, 0x13, 0x19, 0x1B, 0x7F.
  [7] WHITESPACE POSITION: only leading and trailing whitespace is allowed. Whitespace may NOT appear between the sign and the digits, nor between digits, for either ASCII or non-ASCII spaces (Step A turns non-ASCII spaces into ' ', so they inherit the same restriction). Verified: '- 5', '-\t5', '-\xa05', '-　5' all -> invalid int value; '5 5', '5\xa05', '1 2' -> invalid int value. But '\xa0-5' and '　-5' -> ACCEPT -5 (leading whitespace before the sign is fine), and '\xa0 \t-1_٥　' -> ACCEPT -15.
  [8] GATE 2 STEP C (digit-count limit, CPython `sys.int_max_str_digits`, default 4300). After Step A, count the characters matched by [0-9] in t (sign, underscores and whitespace do NOT count; leading zeros DO count). If that count > 4300, REJECT. Verified: 4300 nines ACCEPT / 4301 nines REJECT; '+' or '-' or surrounding whitespace prefixed to 4300 digits still ACCEPT and to 4301 still REJECT; 4300 zeros ACCEPT / 4301 zeros REJECT (so it is a character count, not a magnitude); 300 zeros + 4000 nines (4300 chars) ACCEPT but 301 zeros + 4000 nines (4301 chars) REJECT; '9' repeated 4300 times joined by 4299 underscores (string length 8599) ACCEPT, 4301 digits with underscores REJECT; 4300 Arabic-Indic U+0665 ACCEPT / 4301 REJECT; 4300 astral U+1D7F6 ACCEPT / 4301 REJECT.
  [9] ARBITRARY PRECISION: accepted values are exact Python ints with no 64-bit truncation. A 400-digit input prints all 400 digits verbatim in the output dict. A 4300-digit input prints all 4300 digits (verified digit run length == 4300). Because parsing caps at 4300 digits, the output side never trips the int-to-str limit.
  [10] MIXED SCRIPTS AND SIGNS: digits from different scripts may be freely mixed with each other, with ASCII digits and with underscores. Verified: '1'+U+0665 -> 15; U+0967+U+FF12+'3' -> 123; U+0E55+'_'+'7' -> 57; U+0665+'_'+U+FF17 -> 57. The sign, however, must be ASCII '+' or '-': U+2212 MINUS SIGN, U+FF0B FULLWIDTH PLUS and U+FF0D FULLWIDTH HYPHEN-MINUS are all REJECTED, while ASCII '-' + U+FF15 -> -5 and ASCII '+' + U+0665 -> 5.
