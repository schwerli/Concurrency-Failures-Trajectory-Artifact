PBKDF2 (RFC 2898 §5.2), the only block: U_1 = HMAC_SHA1(P, S || INT_BE32(1)) where INT_BE32(1) is the four bytes 0x00 0x00 0x00 0x01 appended to the salt; then for j = 2..1000, U_j = HMAC_SHA1(P, U_{j-1}); F = U_1 XOR U_2 XOR ... XOR U_1000 (accumulate the XOR as you go, 20 bytes wide). Output the first 16 bytes of F. Exactly 1000 HMAC invocations; an off-by-one (999 or 1001) is the single most likely bug and every corpus entry will catch it.
 6. HMAC-SHA1 (RFC 2104), block size B = 64 bytes: if the key is longer than 64 bytes, replace it with SHA1(key) (20 bytes) FIRST; then right-pad the key with 0x00 up to exactly 64 bytes. ipad = key XOR 0x36 repeated, opad = key XOR 0x5c repeated. HMAC(k, m) = SHA1(opad || SHA1(ipad || m)). A 64-byte key must NOT be hashed (only strictly greater than 64); the corpus has 63/64/65-byte keys in ASCII and in 2-/3-/4-byte UTF-8 forms to pin this down. A zero-length key is legal and becomes 64 zero bytes.

PERFORMANCE: precompute the ipad and opad 64-byte key blocks once per derivation (and ideally the SHA-1 midstate after the first ipad/opad block) because the inner HMAC key is constant across all 1000 iterations. A naive re-pad per iteration still works but the harness spawns 85 processes, so keep each run well under a second.
 8. SHA-1 (FIPS 180-4): five 32-bit words h0..h4 = 0x67452301, 0xEFCDAB89, 0x98BADCFE, 0x10325476, 0xC3D2E1F0.  13. ARGV PARSING — the dash rule (this is argparse's exact behaviour, verified): for the space-separated form, a following token that starts with '-' is accepted as the VALUE only if it is exactly "-", OR it matches /^-\d+$|^-\d*\.\d+$/ (so -1, -0, -1.5, -.5 are values), OR it contains a space character anywhere (so "- x" and "-x y" are values).  14. ARGV PARSING — help short-circuit: -h, --help, and any unambiguous prefix of --help (--h, --he, --hel) print the help text to STDOUT and exit 0 immediately, regardless of position and regardless of missing required options.  15. ARGV PARSING — error precedence and messages, all to stderr with exit 2 and always preceded by the single usage line: (1) 'argument --X: expected one argument' when an option is missing its value; (2) then 'the following arguments are required: --a, --b, --c, --d' listing only the missing ones in a,b,c,d declaration order joined by ', '; (3) only if nothing is missing, 'unrecognized arguments: <leftover tokens joined by a single space>' for unknown options, stray positionals, or a bare '--'.
