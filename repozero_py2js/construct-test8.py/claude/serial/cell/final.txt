## Non-obvious behaviors I probed and matched

- **`bytes` repr quoting** — single quotes preferred; switches to `"` only when the payload has `'` but no `"`; `\\ \t \n \r` named escapes, printable ASCII `0x20–0x7e` literal, `0x7f` and above as `\xNN`. Verified via `--a 39 --b 92` and mixed-quote strings.
- **`len(args.c)` is code points, not UTF-16 units** — `--c 😀` gives "expected 1, found 4", so JS `String#length` would be wrong. Uses code-point iteration.
- **BigInt for `--a`/`--b`** — the range error echoes the value verbatim (`given value 1000000000000000000000000000000`); `Number` would print it in scientific notation.
- **`int()` accepts** surrounding whitespace, `+`/`-`, and `1_0`; rejects `0x10`, `1.5`, `12abc`.
- **argparse value-vs-option** — `--c -5` is accepted as a value (negative-number matcher) but `--c -x` errors with "expected one argument". A bare `--` lands in "unrecognized arguments".
- **Traceback source lines are cwd-dependent** — the frozen binary records the *relative* path `test8.py`, so `linecache` only finds it when cwd contains such a file. Run from `/workspace` the carets vanish; from `/workspace/dataset` they appear. `lib/runtime/traceback.mjs` reproduces this by resolving against `process.cwd()`.

## One judgment call worth flagging

`prog` is pinned to `test8_executable` rather than derived from `basename(argv[1])` (which would yield `test8.mjs`). This makes usage/error text match the reference byte-for-byte, per requirement 3, at the cost of the program naming a file that isn't itself. The parser accepts a `prog` option if you'd rather it self-identify — it's a one-line change in `test8.mjs:22`.
