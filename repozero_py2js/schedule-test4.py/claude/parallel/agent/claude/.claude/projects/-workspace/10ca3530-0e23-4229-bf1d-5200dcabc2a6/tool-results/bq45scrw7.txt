
=========== DIMENSION: --help / -h output and usage-line formatting (byte-exact), COLUMNS/terminal-width wrapping, prog-name derivation, stream & exit-code routing ===========
RULES:
 1. Help/usage text is produced by Python's argparse with default HelpFormatter (Python 3.10-3.12 vintage: header is 'options:', and usage wrap tokens are produced by the old regex splitter so '--a A' splits into '--a' + 'A').
 2. Default (COLUMNS unset / non-tty stdout) help is exactly these 127 bytes: 'usage: test4_executable [-h] --a A --b B --c C\n\noptions:\n  -h, --help  show this help message and exit\n  --a A\n  --b B\n  --c C\n'. Exit 0, stderr empty.
 3. Indentation constants: action lines are indented 2 spaces; the help description for -h starts at 1-based column 15 (2 spaces + '-h, --help' (10 chars) + 2 spaces = offset 14); 'options:' is at column 1; there is exactly one empty line between the usage block and 'options:'; exactly one trailing newline overall; no trailing whitespace anywhere.
 4. --a/--b/--c have no help string, so they are rendered as bare '  --a A' / '  --b B' / '  --c C' with no padding and are NEVER wrapped or reflowed at any width.
 5. width = terminal_columns - 2. terminal_columns = int(os.environ['COLUMNS']) if COLUMNS parses as a Python int and is > 0; otherwise the tty size of the STDOUT file descriptor; otherwise the hard fallback 80. The width source is stdout even when the text is written to stderr.
 6. COLUMNS parsing follows Python int(): optional surrounding whitespace, optional +/- sign, leading zeros, '_' digit separators, and any Unicode decimal digits are accepted. Values that fail to parse, or are <= 0, are ignored (fall through to tty/80). Floats ('40.5') and hex ('0x28') fail to parse.
 7. Usage-line algorithm: build body = prog + ' [-h] --a A --b B --c C'. If 7 + len(body) <= width, emit 'usage: ' + body on one line. Otherwise split into tokens ['[-h]','--a','A','--b','B','--c','C'].
 8. Usage wrap, prog placement: if 7 + len(prog) <= 0.75 * width, prepend prog to the token list, use indent = ' ' * (7 + len(prog) + 1), and strip that indent from the first line (which instead carries the 'usage: ' prefix). Otherwise put prog alone on the first line after 'usage: ' and use indent = ' ' * 7 for every following line.
 9. Usage greedy fill: line_len = 6 (len('usage: ')-1) for the prefixed first line, else len(indent)-1. For each token: if line_len + 1 + len(token) > width AND the current line already has a token, flush the line (indent + ' '.join(tokens)) and reset line_len = len(indent)-1. Then append the token and line_len += 1 + len(token). A single over-long token is emitted on its own line unsplit.
 10. Help-body layout constants for this program: action_max_length = 12 (= 2 + len('-h, --help')); max_help_position = min(24, max(width - 20, 4)); help_position = min(14, max_help_position); action_width = help_position - 4; help_width = max(width - help_position, 11).
 11. If len('-h, --help') = 10 <= action_width, emit '  ' + '-h, --help'.ljust(action_width) + '  ' + first help line, with continuation lines indented help_position spaces. Otherwise emit '  -h, --help\n' and indent every help line by help_position spaces.
 12. Help text 'show this help message and exit' (31 chars) is greedy word-wrapped at help_width; words are never hyphenated or broken.
 13. Concrete COLUMNS thresholds: >=48 usage on one line; >=33 prog stays on the 'usage: ' line with a 24-space hanging indent (<=32 -> prog alone on line 1, 7-space indent); >=36 help text on the same line as '-h, --help' with 14-space continuation indent (<=35 -> own line); >=47 help text unwrapped. Help-line indent for COLUMNS<=35 is min(14, max(COLUMNS-22, 4)), i.e. 4 for COLUMNS<=26 then +1 per column up to 13 at COLUMNS=35.
 14. prog = the substring of argv[0] after the last '/' (POSIX basename without trailing-slash stripping), used verbatim: no symlink/realpath resolution, no extension stripping, no whitespace trimming, spaces/tabs/Unicode preserved. 'dir/', '///' and '' all yield an empty prog, which is dropped from the usage join giving 'usage: [-h] --a A --b B --c C'. The same prog string is reused as the 'PROG: error: ...' prefix.
 15. --help/-h writes only to stdout and exits 0; all argparse errors write only to stderr and exit 2 (stdout empty). Error output is 'usage-block\n' + 'PROG: error: MESSAGE\n' with no blank line between them, and the error message line is never wrapped.
 16. -h/--help short-circuits parsing: required-argument checking, unrecognized-argument checking, and the schedule.every().monday.at() call all never run. It works in any argv position and alongside invalid values.
 17. '--' terminates option processing, so '-h' after '--' is not help. Unambiguous long prefixes (--h, --he, --hel) ARE help; matching is case-sensitive. '--help=X' / '-h=1' are errors ('argument -h/--help: ignored explicit argument'); '-hh' is accepted as a cluster of two -h.
 18. When both a required-args error and an unrecognized-args error apply, argparse reports the required-args error (required checking happens inside parse_known_args, before the leftover check).
SURPRISES:
 * Usage wrapping splits an option from its metavar: the wrap tokens are '--a' and 'A' separately, not '--a A'. At COLUMNS<=13 the usage really prints '--a' and 'A' on separate lines. A naive port that keeps '--a A' atomic will differ at COLUMNS 10-13 and elsewhere.
 * The magic 0.75 float comparison decides whether prog shares the 'usage:' line. It is 7 + len(prog) <= 0.75 * width with real float math, so prog length 51 fits at width 78 (58 <= 58.5) but 52 does not. Integer-rounding this comparison gives wrong output at the boundary.
 * The continuation indent for the -h help text is NOT a constant: it slides from 4 to 14 as COLUMNS goes from <=26 up to 36, via max_help_position = min(24, max(width-20, 4)). Most ports hard-code 24/14 and get every narrow width wrong.
 * help_width has a hard floor of 11 and help_position a hard floor of 4, so output stops changing below COLUMNS=14 and is identical for COLUMNS=1..13 (including COLUMNS=0/negative being treated as unset).
 * There are two different single-line thresholds that do not coincide: at COLUMNS=47 the help text is already unwrapped but the usage line is still wrapped. Assuming one 'wide enough' threshold is wrong.
 * COLUMNS is parsed with Python int(), so '4_0', ' 40 ', '+40', '040', fullwidth '４０' (U+FF14 U+FF10) and Arabic-Indic '٤٠' all mean 40. JS parseInt/Number semantics differ on every one of these, and Number('0x28')=40 would wrongly succeed where Python's int() fails.
 * COLUMNS<=0 (including 0 and negatives) is silently ignored rather than clamped, falling back to the tty size or 80.
 * The terminal width always comes from STDOUT's fd, even for the usage block written to STDERR. Redirecting stdout to a file while stderr is a 30-column tty yields 80-column error output.
 * The 'PROG: error: ...' line is never wrapped, even at COLUMNS=1, while the usage block above it is. Wrapping the whole stderr blob is wrong.
 * prog comes from argv[0] with no symlink resolution and no trailing-slash stripping: a symlink shows the link's own name, and argv[0]='dir/' or '///' yields an EMPTY prog, producing 'usage: [-h] --a A --b B --c C' with a single space after 'usage:' (the empty component is dropped from the join, not rendered as a double space).
 * -h wins over everything, including '--help=x'-style errors elsewhere in argv, required-arg errors, and even bogus --a values; but '--help=x' itself is an error with exit 2. '-h x' exits 0 while '-- -h' exits 2.
 * Writing help to a full/unwritable stdout turns exit 0 into exit 120 with an 'Exception ignored in: <_io.TextIOWrapper name='<stdout>' mode='w' encoding='utf-8'>' + 'OSError: [Errno 28] No space left on device' block on stderr — a JS port that ignores write errors will report 0.
 * The section header is 'options:' (Python 3.10+), not 'optional arguments:' — and there is no ANSI color even with FORCE_COLOR/CLICOLOR_FORCE, so this is not 3.14-era argparse.

=========== DIMENSION: argparse error paths and their precedence (test4_executable: --a/--b/--c all required, type=str; auto -h/--help) ===========
RULES:
 1. prog is os.path.basename(sys.argv[0]) and is interpolated into both the usage line and the '<prog>: error: <msg>' line. Do NOT hardcode 'test4_executable'.
 2. Every argparse failure writes exactly two lines to STDERR and nothing to stdout, then exits 2: '<usage block>\n' then '<prog>: error: <message>\n'. There is no trailing blank line.
 3. The usage block for this parser is 'usage: <prog> [-h] --a A --b B --c C' (metavar = uppercased dest). It is wrapped by textwrap to width (COLUMNS-2); the '<prog>: error:' line is never wrapped.
 4. -h/--help writes the help text to STDOUT and exits 0: 'usage: <prog> [-h] --a A --b B --c C\n\noptions:\n  -h, --help  show this help message and exit\n  --a A\n  --b B\n  --c C\n'. ('options:' heading, i.e. Python >= 3.10.)
 5. PRECEDENCE ORDER (highest first): (1) ambiguous option [raised in the argv pre-scan, before any action runs — beats even an earlier -h]; (2) 'argument X: expected one argument' / 'argument -h/--help: ignored explicit argument R' [raised during left-to-right consumption, leftmost offender only]; (3) -h/--help success exit 0; (4) 'the following arguments are required: ...'; (5) 'unrecognized arguments: ...'; (6) the downstream schedule.ScheduleValueError (exit 1).
 6. Missing-required message: 'the following arguments are required: ' + ', '.join(missing) where missing is filtered from the DECLARATION order list ['--a','--b','--c'] — never command-line order.
 7. Unrecognized message: 'unrecognized arguments: ' + ' '.join(extras) where extras are the raw argv elements in original left-to-right order. No quoting, no escaping, no repr. Empty-string extras produce visible extra spaces; embedded TAB/LF are emitted raw.
 8. Unrecognized args are only ever reported when the required-arg check passes. If any of --a/--b/--c is absent, unknown tokens are silently discarded.
 9. Prefix abbreviation is enabled: --h, --he, --hel, --help all invoke help. Matching is exact-prefix and case-sensitive; --hell, --helpp, --H, --A do not match anything.
 10. '--=' and '--=<anything>' produce 'ambiguous option: <raw token> could match --help, --a, --b, --c' (long options only, --help first, then declaration order), exit 2. This is the highest-priority error.
 11. The first '--' disables option parsing for all remaining tokens (no help, no ambiguity check, no option matching), and '--' itself is NOT stripped (no positionals are declared), so it appears verbatim in the unrecognized list. Consequence: a fully valid command line plus a trailing '--' exits 2.
 12. '--' is never accepted as an option value: '--a -- v' gives 'argument --a: expected one argument'.
 13. Token classification for values: a token is treated as a VALUE (not an option) if it does not start with '-', OR it matches ^-\d+$ or ^-\d*\.\d+$ (Unicode-aware \d, so '-٥' qualifies), OR it contains a space character. Otherwise it is an option-looking token and a preceding option gets zero values.
 14. '--name=value' splits on the FIRST '=' only; '--a=' yields the empty string as a valid value (no argparse error; it then fails in schedule with exit 1).
 15. Repeated options: last occurrence wins; earlier values are discarded unvalidated.
 16. 'expected one argument' text is 'argument <option-string-as-written>: expected one argument' — it echoes the option string the user typed (--a/--b/--c here).
 17. 'ignored explicit argument' text names the action by all its option strings joined with '/': 'argument -h/--help: ignored explicit argument <repr(value)>' with Python single-quote repr. Triggered only by the '=' form (-h=1, --help=x, --h=1, --he=x).
 18. A single-dash cluster without '=' is split into short options: '-hx', '-hh', '-h5' all fire help and exit 0 (leftover chars go to extras but help exits first). Unknown clusters like '-x5', '-ab' just become extras.
 19. Unknown options never produce an 'invalid/unknown option' error — they always fall through to extras. Single-dash '-a'/'-b'/'-c' are NOT aliases for '--a'/'--b'/'--c'.
 20. nargs is 1 for each option: a second bare token after a satisfied option becomes an extra, not an error about that option.
 21. Locale env vars have no effect (no gettext catalogs in the frozen bundle); messages are always English.
SURPRISES:
 * Missing-required MASKS unrecognized args entirely. A naive port that collects both and reports the unrecognized ones first (or reports both) will diverge on very common inputs like `--d z`.
 * A trailing bare `--` on an otherwise perfect command line causes exit 2 with 'unrecognized arguments: --'. The `--` is NOT swallowed, because the parser declares zero positionals. Most ports assume `--` always disappears.
 * `--=` (and `--=anything`) is an AMBIGUOUS-OPTION error, not an unrecognized arg: 'ambiguous option: --= could match --help, --a, --b, --c'. The candidate list contains only long options, with --help first.
 * The ambiguous-option error is raised in argparse's pre-scan pass, so it beats a valid `-h` that appears EARLIER on the command line: `-h --=` exits 2 with the ambiguity error instead of printing help.
 * `-hx` prints help and exits 0, but `-h=1` exits 2 with "ignored explicit argument '1'". The presence of the `=` separator is the whole difference (this is the Python 3.13 `sep`-aware code path).
 * Negative numbers are accepted as option VALUES: `--a -5`, `--a -5.5`, `--a -.5`, `--a -0`, `--a -05` all pass through to schedule. But `--a -5.`, `--a -1e5`, `--a -5:5`, `--a -x5` all fail with 'argument --a: expected one argument'. The exact matcher is ^-\d+$ | ^-\d*\.\d+$ with UNICODE \d — so `--a -٥` (U+0665) is also accepted as a value.
 * Whether a `-`-leading token is an option depends on whether it CONTAINS A SPACE: `-x y` as one argv element is a value/extra, while `-xy` is an option. Likewise the single element `--a 10:30` is never parsed as the option --a.
 * `--a=` is legal and sets --a to the empty string (exit 1 from schedule), whereas `--a` with no following token is exit 2 'expected one argument'. Two very different outcomes for what looks like the same 'no value' case.
 * The unrecognized-args list is space-joined with zero quoting, so an empty-string extra leaves a trailing space before the newline ('unrecognized arguments: \n') and a multi-word extra is indistinguishable from several extras.
 * The usage line (and only the usage line) is wrapped to COLUMNS-2. With COLUMNS=20 the missing-required error becomes a 4-line stderr payload. The 'prog: error: ...' line is never wrapped no matter how narrow.
 * prog comes from basename(argv[0]), so renaming/symlinking the binary changes every error message; exec'ing it as 'lnk' yields 'usage: lnk ...' and 'lnk: error: ...'.
 * Help beats everything except the pre-scan ambiguity and a starved earlier option: `--d z -h` exits 0 with help, but `--a -h` exits 2 with 'argument --a: expected one argument'.
 * argparse always wins over the schedule error: `--a 99:99 ... --d` is exit 2 (unrecognized), not exit 1 (ScheduleValueError). Ports must fully finish parsing/validating argv before touching the time value.

=========== DIMENSION: Second error path (hour numerically out of 0..23) and additional/third error paths in /workspace/dataset/test4_executable ===========
RULES:
 1. The hours error (schedule/__init__.py line 547) fires iff the input passes the format regex AND the numeric value of the two hour characters is >= 24. Since the regex is ^[0-2]\d:[0-5]\d(:[0-5]\d)?$ with an ASCII-literal [0-2] first char, the value range is 0..29 and the only failing values are 24,25,26,27,28,29.
 2. Complete ASCII enumeration (verified exhaustively over all 100 HH pairs with MM=00): HH in {00..23} -> exit 0 success; HH in {24,25,26,27,28,29} -> hours error exit 1; HH in {30..99} -> format error exit 1. Exactly 6 of 100 ASCII hour strings reach the second error path.
 3. The second hour character may be ANY Unicode decimal digit (category Nd), in any script, including 4-byte/astral codepoints, and may mix scripts with the ASCII first char. Its decimal value is what counts. So the full hour set reaching the hours error is: ASCII '2' followed by any Nd character whose decimal value is 4,5,6,7,8 or 9 — verified across 67 Nd blocks (Arabic-Indic, Extended Arabic-Indic, NKo, Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada, Malayalam, Sinhala, Thai, Lao, Tibetan, Myanmar, Khmer, Mongolian, Limbu, New Tai Lue, Balinese, Sundanese, Lepcha, Ol Chiki, Vai, Saurashtra, Kayah Li, Javanese, Myanmar Tai Laing, Cham, Meetei Mayek, Fullwidth, Osmanya, Hanifi Rohingya, Brahmi, Sora Sompeng, Chakma, Sharada, Khudawadi, Newa, Tirhuta, Modi, Takri, Ahom, Warang Citi, Dives Akuru, Bhaiksuki, Masaram Gondi, Gunjala Gondi, Mro, Tangsa, Pahawh Hmong, Mathematical Bold/Double-struck/Sans/Sans-bold/Monospace, Nyiakeng Puachue Hmong, Wancho, Adlam, Segmented). No exceptions found.
 4. The first hour character is restricted to ASCII 0x30-0x32. A Unicode digit there always yields the FORMAT error, never the hours error.
 5. The one-trailing-newline tolerance of '$' composes with the hours error: '24:00\n' and '24:00:00\n' produce the hours error at line 547. Two trailing newlines, a trailing space, TAB, CR, VT, FF, or a leading newline all fall back to the format error at line 514.
 6. The hour range check happens before int(minute) and int(second), so an out-of-range hour always wins over anything in the minute/second fields.
 7. The hours-error message contains a LITERAL two-byte '{}' (od -c: '{' '}'), never a substituted number. Confirmed identical for 24:00, 25:30, 26:59, 27:00:00, 28:15:45, 29:59:59, '24:00\n', and Arabic-Indic / Fullwidth / Math-bold / Thai variants — md5 of stderr with the [PYI- line removed is d9e64036fc78437c26e3bad27e9a76dc for all of them.
 8. Hours-error stderr, byte-exact (\n line endings, trailing \n, no BOM):
'Traceback (most recent call last):\n' (34 chars + LF)
'  File "test4.py", line 10, in <module>\n' (39 + LF, two leading spaces)
'  File "schedule/__init__.py", line 547, in at\n' (46 + LF)
'schedule.ScheduleValueError: Invalid number of hours ({} is not between 0 and 23)\n' (81 + LF)
'[PYI-<pid>:ERROR] Failed to execute script \'test4\' due to unhandled exception!\n'
Total size = 278 + len(str(pid)) bytes. stdout is empty. exit 1.
 9. Format-error stderr is identical except the third line says 'line 514' and the fourth line is 'schedule.ScheduleValueError: Invalid time format for a daily job (valid format is HH:MM(:SS)?)' (94 chars). Total size = 291 + len(str(pid)) bytes.
 10. Both tracebacks have exactly TWO frames and contain NO echoed source line and NO caret '^' line (PyInstaller ships no source, so Python's fine-grained error locations are suppressed). grep -c '\^' returns 0.
 11. The <n> in '[PYI-<n>:ERROR]' is the process PID and changes on every invocation. Verified by exec-ing the program from a shell whose $$ was printed first: shellpid 8322 -> PYI-8325. It must be modelled as a varying integer, not a constant.
 12. The traceback filename 'test4.py' and the quoted script name 'test4' in the PYI line are baked into the bundle: they do not change when the executable is renamed, symlinked, or given a bogus argv[0].
 13. THIRD ERROR PATH = argparse, exit code 2, stderr only, no traceback and no [PYI-...] line, two lines: 'usage: <prog> [-h] --a A --b B --c C' then '<prog>: error: <detail>'. <prog> is basename(argv[0]). Details observed: 'the following arguments are required: --a, --b, --c' (and subsets), 'argument --a: expected one argument', 'unrecognized arguments: <tokens>'.
 14. argparse runs before schedule, so any argparse error masks the hour check entirely: '--a 24:00' alone exits 2, not 1.
 15. Any --a value beginning with '-' (e.g. '-1:00', '-24:00', '--b') is treated as an option token and produces 'argument --a: expected one argument' (exit 2). Negative hours are unreachable through the CLI.
 16. --help / -h short-circuits everything: exit 0, help text on STDOUT, stderr empty — even with an out-of-range --a and even with --b/--c missing.
 17. There is NO fourth input-driven exception. int() never raises ValueError (re \d and int() agree exactly on category Nd); the minutes and seconds range errors and datetime.time()'s ValueError are unreachable because the regex caps MM and SS at 59; TypeError('at() should be passed a string') is unreachable because argparse always supplies str.
 18. Environment-driven extra paths exist but are not input-dependent: stdout on /dev/full -> exit 0 plus 'OSError: [Errno 28] No space left on device' from frame 'File "<string>", line 1, in <module>' plus an 'Exception ignored in: <_io.TextIOWrapper name=<stdout> mode=w encoding=utf-8>' block; stdout closed (>&-) -> "AttributeError: 'NoneType' object has no attribute 'flush'"; stdout to a closed pipe -> 'BrokenPipeError: [Errno 32] Broken pipe'. In the hour-24 case with stdout closed, both the schedule traceback+PYI line and the flush error are emitted.
 19. Behaviour is locale- and PYTHON*-env independent: LC_ALL=C with PYTHONUTF8=0 and PYTHONCOERCECLOCALE=0, LC_ALL=en_US.ISO-8859-1, PYTHONWARNINGS=error, PYTHONVERBOSE=1, and TMPDIR=/nonexistent all leave the classification unchanged. Invalid UTF-8 bytes in --a decode via surrogateescape and land on the format error.
 20. Exit codes are exactly {0 success/help, 1 any unhandled Python exception, 2 any argparse error}. 126 only appears when the kernel refuses the exec (argv > ~2MB, E2BIG) — that is the shell's code, not the program's.
 21. --b and --c are parsed but never used: any values (empty string, embedded newline, '99:99', '24:00') have zero effect on the outcome. Duplicate --a is allowed and the LAST occurrence wins ('--a 23:00 --a 24:00' -> hours error).
SURPRISES:
 * '2X' does not mean out-of-range. Hours 20-23 succeed; only 24-29 error. A port that treats a leading '2' as suspicious is wrong.
 * The hours error message is emitted with an UNFORMATTED literal '{}' — bytes 0x7b 0x7d. It never contains the offending number, so the error text is identical for 24, 25, 29, and for Unicode-digit hours. A port that interpolates the value (e.g. 'Invalid number of hours (24 is not between 0 and 23)') is byte-wrong.
 * The regex's [0-2] is ASCII-only but its \d is full-Unicode, so the two hour characters have ASYMMETRIC alphabets. '2' + ARABIC-INDIC FOUR reaches the hours error while ARABIC-INDIC TWO + '4' reaches the format error. A JS port using /^[0-2]\d:[0-5]\d(:[0-5]\d)?$/ (JS \d is ASCII-only) would send every Unicode-digit input to the format error.
 * int() happily parses mixed-script decimal digits ('2' + Devanagari 4 == 24), including 4-byte astral digits like MATHEMATICAL BOLD DIGIT FOUR and Osmanya. JS Number()/parseInt() reject all of these.
 * Exactly one trailing '\n' is tolerated and still reaches the hours error ('24:00\n' -> line 547), but two newlines fall back to the format error. Note that bash command substitution $(printf '24:00\n') silently strips the newline — testing this requires $'24:00\n'.
 * The '[PYI-<n>]' number is the PID, so it differs on every single run. Golden-file comparisons must mask it. Total stderr length therefore varies with PID digit count (281 bytes with a 3-digit PID, 283 with 5 digits for the hours error).
 * The traceback has NO source-code line and NO caret '^' line even though the Python is >= 3.10 (argparse prints 'options:'), because PyInstaller strips the sources. A port that renders 'job = schedule.every().monday.at(args.a)' and a caret is wrong.
 * Frame filenames are the short, relative 'test4.py' and 'schedule/__init__.py' — not absolute paths, and not affected by renaming the executable.
 * Failing to write stdout does NOT change the exit code: '>/dev/full' and '| true' both exit 0 while dumping an OSError/BrokenPipeError traceback plus an 'Exception ignored in: <_io.TextIOWrapper ...>' block to stderr, from a phantom frame 'File "<string>", line 1, in <module>'.
 * argparse fires before schedule, so '--a 24:00' with --b/--c missing exits 2 with no traceback — a port that validates the time first would wrongly exit 1.
 * '--a -24:00' and '--a -1:00' never reach schedule at all: argparse eats the leading dash and says 'expected one argument' (exit 2). There is no path to a negative hour.
 * The usage/prog string is basename(argv[0]) ('test4_executable' here, but 'ZZmyname' for a renamed copy, and empty for an empty argv[0]), while the PYI line always says 'test4'. Two different name sources in one program.
 * No minutes/seconds range error and no int() ValueError exist at all — the regex makes them dead code. Scanning 67 Unicode Nd blocks produced zero deviations, so a port only needs the two schedule messages plus argparse.
 * Behaviour survives LC_ALL=C with PYTHONUTF8=0 and PYTHONCOERCECLOCALE=0 — PyInstaller pins UTF-8 argv decoding, so Unicode-digit hours still reach the hours error even in the C locale.

=========== DIMENSION: Accept/reject boundary of the --a time string, and which of the two ScheduleValueError messages is produced ===========
RULES:
 1. DECISION PROCEDURE (reproduces every observed result). Let s = the decoded --a value (argv bytes decoded as UTF-8 with surrogateescape). Step 1: if re.match(r'^[0-2]\d:[0-5]\d(:[0-5]\d)?$', s) is None -> emit the FMT traceback (schedule/__init__.py line 514, 'schedule.ScheduleValueError: Invalid time format for a daily job (valid format is HH:MM(:SS)?)'), empty stdout, exit 1. Step 2: hour = int(s.split(':')[0]); if not (0 <= hour <= 23) -> emit the HOURS traceback (line 547, 'schedule.ScheduleValueError: Invalid number of hours ({} is not between 0 and 23)' with LITERAL braces), empty stdout, exit 1. Step 3: print 'Job(interval=1, unit=weeks, do=None, args=(), kwargs={})\n', exit 0.
 2. REGEX SEMANTICS, precisely: it is re.match (or re.search) with an explicit '$', NOT re.fullmatch. Consequence: the pattern matches when the string ends at the '$' OR when exactly one U+000A follows at the very end of the string. Nothing else may follow that LF.
 3. CHARACTER CLASSES ARE ASYMMETRIC BY POSITION. Position 1 (hour tens) accepts ONLY ASCII U+0030..U+0032. Position 2 (hour units) accepts ANY character in Unicode general category Nd. Position 3 is literally ':'. Position 4 (minute tens) accepts ONLY ASCII U+0030..U+0035. Position 5 (minute units) accepts ANY Nd. If a third component is present, position 6 is ':', position 7 (second tens) accepts ONLY ASCII U+0030..U+0035, position 8 (second units) accepts ANY Nd.
 4. NUMERIC VALUE, NOT CODEPOINT, IS USED. hour = 10*value(c1) + value(c2) where value() is the Unicode decimal digit value. So '2' + U+0665 (Arabic-Indic 5) == hour 25, '2' + U+1D7D3 (math bold 5) == hour 25, '2' + U+096B (Devanagari 5) == hour 25. Verified across 54 distinct Nd blocks (37 BMP + 17 non-BMP), all uniform.
 5. REACHABLE HOUR VALUES ARE EXACTLY 0..29 (tens digit ASCII 0-2, units digit Nd value 0-9). Therefore: HOURS error <=> hour in 24..29 <=> hour tens char is ASCII '2' AND hour units char is an Nd digit whose numeric value is 4..9. Everything else that passes the regex succeeds.
 6. MINUTES AND SECONDS CAN NEVER BE OUT OF RANGE. Their tens digit is ASCII-restricted to 0-5 and their units digit is Nd value 0-9, so the maximum is 59. Consequently 'Invalid number of minutes' and 'Invalid number of seconds' are UNREACHABLE. Exhaustive MM=00..99 and SS=00..99 sweeps produced only OK (00-59) and FMT (60-99). Exactly two distinct error messages exist for this program.
 7. EXACT COMPONENT WIDTH. Each colon-separated component must be exactly 2 characters. 1-digit ('1:30', '10:5'), 3-digit ('010:30', '10:030'), and 0-digit ('10:', ':30') components are all FMT. Exactly 2 or exactly 3 components; 1 component or 4+ components are FMT even when each part is in range ('10:30:45:00' -> FMT).
 8. WHITESPACE: only U+000A, only one of it, only at the absolute end. All of these are FMT: leading LF, leading/trailing space, trailing CR, TAB, VT (U+000B), FF (U+000C), FS (U+001C), RS (U+001E), CRLF, LFCR, two-or-more LFs, U+0085 NEL, U+2028 LINE SEPARATOR, U+2029 PARAGRAPH SEPARATOR, U+00A0 NBSP, U+200B ZWSP, U+FEFF BOM, and any LF that is not the final character.
 9. NON-Nd NUMERICS ARE REJECTED BY THE REGEX (FMT, line 514), never reaching int(): superscripts (U+00B2/B3/B9, U+2070, U+2074), subscripts (U+2080, U+2085), vulgar fractions (U+00BD, U+2153, U+215D, U+215F), Roman numerals (U+2160, U+2162), circled/dingbat numbers (U+2460, U+2465, U+24EA, U+2776), CJK/ideographic numerals (U+3007, U+3021, U+4E00, U+4E09, U+3405), enclosed CJK (U+3220, U+32B1), and archaic numerals (U+10107, U+10A40, U+12400, U+1D360, U+1F101). General categories No and Nl do not match \d.
 10. SIGNS AND ALTERNATE SEPARATORS: '+', '-', U+2212 MINUS are all FMT (the regex blocks them before int() sees them, so int()'s sign handling is dead code here). Only ASCII ':' (U+003A) separates; a full sweep of ASCII 32..126 in the separator slot found ':' as the sole non-FMT value, and U+FF1A FULLWIDTH COLON is FMT.
 11. OUTPUT SHAPE: on success stdout is always the identical 57 bytes 'Job(interval=1, unit=weeks, do=None, args=(), kwargs={})\n' and stderr is empty; the time value never appears in output. On either error stdout is empty (0 bytes) and exit code is 1.
 12. STDERR SHAPE (both error paths): line 1 'Traceback (most recent call last):', line 2 '  File "test4.py", line 10, in <module>', line 3 '  File "schedule/__init__.py", line 514, in at' (FMT) or 'line 547, in at' (HOURS), line 4 the 'schedule.ScheduleValueError: ...' message, line 5 '[PYI-<pid>:ERROR] Failed to execute script 'test4' due to unhandled exception!'. The <pid> in line 5 varies per run and is the only non-deterministic part.
 13. ARGUMENT PLUMBING: --b and --c values never affect the decision (they may be invalid times or empty strings). A repeated --a uses the last occurrence. Values beginning with '-' must be passed as --a=VALUE; with the separated form argparse exits 2 with 'argument --a: expected one argument' before schedule is reached.
 14. EQUIVALENT IMPLEMENTATION-FRIENDLY RESTATEMENT: t = s[:-1] if s ends with one '\n' else s; require a FULL match of ^[0-2]\p{Nd}:[0-5]\p{Nd}(:[0-5]\p{Nd})?$ against t (with [0-2]/[0-5] as ASCII-only ranges and \p{Nd} unicode-aware); if it fails -> FMT; else hour = 10*digitValue(t[0]) + digitValue(second hour char); if hour > 23 -> HOURS; else success.
SURPRISES:
 * JS regex `\d` is ASCII-only. A naive port using /^[0-2]\d:[0-5]\d(:[0-5]\d)?$/ would reject '1٠:30', '10:3٠', '2５:00' etc., which the original ACCEPTS (or converts to an HOURS error). You must use /\p{Nd}/u in positions 2, 5 and 8 while keeping [0-2] and [0-5] as ASCII-only ranges in positions 1, 4 and 7. Using \p{Nd} in the tens positions too would wrongly accept '２0:00'.
 * JS `$` does NOT tolerate a trailing newline, but Python's does. '10:30\n' and '10:30:45\n' SUCCEED here (exit 0). A JS port must strip at most one trailing '\n' before matching. Stripping with .trim() or /\s+$/ would be wrong: it would wrongly accept '10:30\r', '10:30\t', '10:30 ', and '10:30\n\n' -- all of which are FMT.
 * The trailing-newline tolerance is ASYMMETRIC: a trailing LF is fine, a LEADING LF is FMT. Also nothing may follow the tolerated LF ('10:30\nx' is FMT).
 * parseInt('2٥') returns 2 in JS (it stops at the first non-ASCII char), and Number('2٥') is NaN. The original yields 25 and an HOURS error. You must convert Nd digits by their Unicode decimal value, e.g. codePoint - blockZeroCodePoint, not via parseInt/Number.
 * Non-BMP Nd digits (U+1D7CE.., U+104A0.., U+1FBF0..) are fully accepted and correctly valued. In JS these are surrogate pairs, so any index-based or .length-based component validation will miscount: '2' + U+1D7D3 + ':00' has JS .length 7, not 6. Iterate by code points.
 * The hours message contains a LITERAL '{}' -- 'Invalid number of hours ({} is not between 0 and 23)'. It is an unformatted Python format string (the schedule library forgot .format(hour)). Do not substitute the actual hour; do not treat it as a placeholder.
 * There are only TWO error messages. 'Invalid number of minutes' and 'Invalid number of seconds' are structurally unreachable because the regex caps minutes and seconds at 59. Porting the library's full validation chain would add dead branches; porting it *wrongly* (e.g. allowing \p{Nd} in the tens slot) would make them reachable and diverge.
 * The HOURS band is exactly 24-29, a narrow 6-value window. 30:00 through 99:00 produce the FMT error, not the hours error, because [0-2] rejects the tens digit first. A port that validates range before shape would emit the wrong message for 30-99.
 * The regex is re.match with '$', not re.fullmatch -- this is the only reason the trailing LF works. Also note the code then does split(':') without any component-length re-check, so the minute component can legitimately be the 3-character '30\n' and int() silently strips it. A port that asserts len(component)==2 after splitting would break '10:30\n'.
 * Whitespace-looking Unicode is NOT newline for '$': U+2028, U+2029 and U+0085 are all FMT. A port using a Unicode-aware line-terminator notion (JS regex /$/ with /m/, or JS's own line terminators which DO include U+2028/U+2029) would wrongly accept them.
 * stdout on success is a constant string that does not depend on the time at all -- '00:00', '23:59', '10:30:45' and '1٢:3٤:4٥' all print byte-identical output. Don't build the repr from the parsed time.
 * Invalid UTF-8 bytes in argv must not raise: Python decodes with surrogateescape, and the lone surrogates simply fail the regex (FMT, exit 1). A port that throws on invalid UTF-8 would use the wrong exit path.
 * 4-component input like '10:30:45:00' is FMT even though every component is valid -- the regex has no third optional group. Don't implement 'split on colon, validate each part' without a component-count check of exactly 2 or 3.
 * NUL bytes inside the value are physically unreachable through argv, so there is no observable behavior to port; ignore the case rather than inventing one.
 * stderr always ends with a PyInstaller line '[PYI-<pid>:ERROR] Failed to execute script 'test4' due to unhandled exception!' whose pid changes every run. Any byte-exact stderr comparison in tests must normalize that number. (A rare transient '[PYI-<pid>:WARNING] Failed to remove temporary directory' was observed once out of hundreds of runs; 60/60 repeats of the same input were stable, so it is environment noise, not program behavior.)

=========== DIMENSION: process-level and encoding behavior ===========
RULES:
 1. Success: stdout is EXACTLY the 57 bytes "Job(interval=1, unit=weeks, do=None, args=(), kwargs={})\n" — one and only one trailing LF, no CR, no BOM. stderr is exactly empty. Exit 0.
 2. Exit codes are only 0 (success), 1 (schedule.ScheduleValueError from an unhandled exception), and 2 (argparse usage error). Never 126/127 from the program itself (those come from the shell when execve fails).
 3. stdout and stderr are never both non-empty in the same run, EXCEPT when writing to stdout fails; therefore stdout/stderr interleaving order is unobservable and a port need not model it. On the error path stdout is always 0 bytes.
 4. stdout is block-buffered when redirected to a file or pipe (the data is written at interpreter shutdown, not at print()); a write failure at that point produces stderr noise but leaves the exit code at 0.
 5. argv is always decoded as strict UTF-8 with surrogateescape for undecodable bytes, and stdout/stderr are always UTF-8 (with backslashreplace on stderr). This is fixed: LANG, LC_ALL, LC_CTYPE, PYTHONIOENCODING, PYTHONUTF8 and every other PYTHON* variable are ignored (PyInstaller isolated config). A port must hardcode UTF-8 and must not consult the locale.
 6. A NUL byte in the --a value truncates it at the C string boundary: the program sees only the bytes before the first NUL. '12:30\0anything' succeeds; '25:00\0z' gives the hour-range error; a leading NUL yields an empty --a.
 7. Invalid UTF-8, overlong encodings (\xc0\xb1) and encoded surrogates (\xed\xa0\x80) become surrogate-escape code points that never satisfy [0-2]/[0-5]/\d, so they always give 'Invalid time format', exit 1 — never a decoding crash.
 8. \d accepts any Unicode Nd digit INCLUDING non-BMP ones (e.g. U+1D7D8 MATHEMATICAL DOUBLE-STRUCK DIGIT ZERO, 4-byte UTF-8), and int() converts them. In JS this means iterating code points, not UTF-16 units, and using a Unicode-aware \p{Nd} class. The literal classes [0-2] and [0-5] remain ASCII-only.
 9. --b and --c are never read, validated, printed, or decoded-checked. Any value at all (empty, tabs, invalid UTF-8, emoji, 1 MB) is fine; only their PRESENCE is required. Passing a value that is itself a known flag (e.g. --b --a) makes argparse consume it as a flag and fail with exit 2.
 10. Output is fully deterministic with respect to time, date and TZ. The Job repr contains no timestamp and does not echo the parsed time, so every accepted --a value yields byte-identical stdout.
 11. The last stderr line on the exception path is '[PYI-<pid>:ERROR] Failed to execute script \'test4\' due to unhandled exception!' with the live OS PID of the child process. A port must emit this line but its number is not reproducible; comparisons must mask it. Total error stderr length = 291 + number-of-digits-in-pid bytes in a clean cwd.
 12. This PYI trailer is emitted ONLY when the script body raises. It is absent for argparse exit-2 errors and absent for stdout-flush failures (which exit 0).
 13. The traceback body depends on the CURRENT DIRECTORY: if ./test4.py is readable, line 10 of it is lstripped, re-indented with 4 spaces and inserted after the '  File "test4.py", line 10, in <module>' frame, followed by an anchor line of 10 spaces + min(34, max(0, len(line10)-5)) carets. The same applies to ./schedule/__init__.py line 514. In a clean directory both source lines are omitted. PYTHONPATH cannot inject them.
 14. argparse's prog name is os.path.basename(sys.argv[0]); usage and error lines follow argv[0], so renaming/copying/symlinking the executable or spoofing argv[0] changes the exit-2 text. An argv[0] whose basename is empty produces 'usage: [-h] ...' and ': error: ...'.
 15. Usage/help line wrapping width = (int(COLUMNS) if valid and > 0 else tty width of the output else 80) minus 2, i.e. a default text width of 78 columns. The 'error: the following arguments are required: --a' line is never wrapped. Success stdout is unaffected.
 16. The program never reads stdin: it behaves identically with stdin from a file (bytes left unconsumed), /dev/null, or fd 0 closed.
 17. No files are created in the cwd. The only filesystem side effect is /tmp/_MEI<6 chars> (~16 MB), created at startup and removed at exit; TMPDIR is ignored so /tmp specifically must be writable. Parallel invocations are independent and leak nothing.
 18. A single argv string is capped at 131071 bytes by Linux MAX_ARG_STRLEN; 131071 reaches the program, 131072 or more fails in execve (E2BIG) so the program never starts. A port should not attempt to replicate this — it is the OS, not the app.
SURPRISES:
 * A NUL byte silently truncates --a rather than erroring: '--a 12:30\0garbage' SUCCEEDS with exit 0. A JS port using Buffers or reading argv from a source that preserves NUL would see the garbage and reject it. Node's process.argv already truncates at NUL, so this happens to match — but only by accident.
 * The exception-path stderr is NOT byte-reproducible: it embeds the live child PID in '[PYI-<pid>:ERROR]'. Any golden-file test must mask it, and the total byte length changes with the PID's digit count (295 vs 296 bytes for the same logical error).
 * The traceback text changes depending on the CURRENT DIRECTORY. Run from /workspace/dataset it is 422 bytes and contains the Chinese comment '创建每周一特定时间作业' from the source file; run from an empty directory it is 295 bytes with no source lines. Worse, an attacker-controlled ./test4.py in the cwd gets echoed verbatim into stderr. A port that hardcodes one of the two forms will mismatch half the time.
 * The caret anchor line's width is computed from the LOCAL file's line 10 length (10 spaces + min(34, len-5) carets), and when that line is shorter than 6 chars the anchor line is 10 spaces of pure trailing whitespace.
 * Every PYTHON* env var is ignored, including PYTHONIOENCODING=bogus-codec-xyz which would normally make CPython refuse to start. A port that honors an encoding env var, or a test harness that tries to force ASCII output, will diverge.
 * LC_ALL=C does not degrade anything: Unicode digits in --a still work and stdout stays UTF-8. Porters often assume the C locale forces ASCII.
 * \d matches non-BMP Unicode digits such as U+1D7D8 (𝟘). A JS port using /\d/ (ASCII-only) or non-'u'-flagged regexes over UTF-16 units will reject inputs the original accepts, and code-unit indexing will split the surrogate pair.
 * Overlong UTF-8 and encoded surrogates are rejected rather than normalized, so '1\xc0\xb1:30' fails even though \xc0\xb1 is an overlong '1'. A lenient JS UTF-8 decoder that accepts overlongs would wrongly succeed.
 * Failure to write stdout (/dev/full, closed fd 1, broken pipe) leaves the EXIT CODE AT 0 while emitting a traceback on stderr. With fd 1 closed, sys.stdout is None and print() silently no-ops, producing an AttributeError about 'flush' rather than anything about printing. A port that exits non-zero on EPIPE/ENOSPC will differ.
 * SIGPIPE is ignored, so the process is never killed by signal 13; it prints BrokenPipeError and exits 0. Node kills on EPIPE differently.
 * argparse's prog name comes from argv[0]'s basename, so the exit-2 usage text is not a constant — copy the binary to a different filename and 'usage: test4_executable ...' becomes 'usage: <newname> ...'.
 * Usage wrapping silently depends on COLUMNS or the tty width (default text width 78, not 80). The same exit-2 error produces 114, 128 or 138 bytes depending on the environment.
 * Invalid bytes echoed back by argparse appear as the literal ASCII text '\udcff\udcfe' (backslashreplace), not as raw bytes and not as U+FFFD replacement characters.
 * Capturing output through a pty adds \r before every \n (58 bytes instead of 57 for the success line). That is terminal ONLCR, not the program — easy to bake into a wrong expected value.
 * Under a pty the success line is 'Job(...)\r\n' but stderr is still empty, so a naive tty-based golden capture will look plausible while being wrong at the byte level.
