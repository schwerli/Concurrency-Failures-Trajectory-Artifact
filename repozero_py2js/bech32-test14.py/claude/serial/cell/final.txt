## Behaviour recovered from the executable (black-box probing)

`convertbits` behaves as an MSB-first sliding-bit accumulator with `pad=True`:
- accumulator is masked with `(1 << (frombits + tobits - 1)) - 1`, output values with `(1 << tobits) - 1`;
- a negative or too-wide value makes the whole call return `None` → the chained second call then raises `TypeError: 'NoneType' object is not iterable` (frame `bech32/__init__.py`, line 90), exit 1;
- shift widths are computed **before** the input is iterated, so `--c -5` fails at line 88 and `--b -8` at line 89 with `ValueError: negative shift count`, even when `data` is `None`;
- `--c 0` makes the reference hang (infinite loop) — the port reproduces that rather than papering over it;
- arbitrary precision is real: `--b 64 --c 40` prints `1095216660480`, so every value is a `BigInt`.

Two notes on fidelity worth flagging:
- stderr comparison required PID normalization, since the reference embeds its own PID in `[PYI-###:ERROR]`; the port uses `process.pid` there.
- The reference's traceback shows source/caret lines only when `test14.py` is readable from the cwd (the frozen bundle has no copy). Initially 22 cases mismatched on exactly this; `pytraceback.mjs` now probes for the file, and the suite passes from both `/output` and `/workspace/dataset`.

Constraints met: pure ESM with `.mjs` suffixes throughout, zero npm dependencies, `node:fs` as the only import that is not a local file, and no use of `Uint8Array`/`DataView`.
