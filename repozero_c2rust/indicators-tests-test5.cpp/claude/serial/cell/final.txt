## What I did

**Black-box inference.** The library header wasn't present in the dataset at all, so I derived the contract purely from call sites plus binary output:

| C++ call | Output | Inferred behavior |
|---|---|---|
| `builder.set_progress(60).set_total(200).build()` | `30.0%` | chainable setters; `build()` = ratio → percentage, 1 decimal |
| `tracker.get_progress()` | `1/3` | `"{progress}/{total}"` |
| `tracker.get_percentage()` | `33.3%` | ratio → percentage, 1 decimal |
| `Format::percentage(0.33f)` | `33.0%` | takes a 0–1 fraction, ×100, default precision 1 |
| `Format::percentage(0.66f, 2)` | `66.00%` | optional precision arg |

**The one real correctness risk** was float rounding. Rather than assume, I diffed C++ `std::fixed`/`setprecision` against Rust `{:.*}` across 48 cases including exact binary ties (`0.25`, `0.125`, `2.5`, `66.665`). They agree byte-for-byte — both round-half-to-even on the exact binary value — so I used Rust's native formatting instead of hand-rolling rounding logic.

**Two bugs I hit and fixed:**
1. `cargo build` passed but bare `rustc test5.rs` failed — bare `rustc` defaults to **edition 2015**, where `use builder::X` resolves from the crate root instead of the enclosing module. Adding `self::` prefixes makes it compile under both editions, so the requirement's "either `rustc` or `cargo`" both genuinely work.
2. Dead-code warnings from unused accessors. I deleted the builder's `progress()`/`total()` (nothing used them) rather than blanket-silencing, and scoped `#![allow(dead_code)]` to the library module for the tested-but-not-called-by-main surface.

## Results

- `rustc test5.rs`, `rustc --edition 2021`, and `cargo build --release` all compile **warning-free**
- 9/9 unit tests pass
- Output is **byte-identical** to the C++ binary (29 bytes, verified with `cmp` and `od`), with matching exit codes across 5 argument sets

## Two judgment calls worth flagging

Both concern behavior the fixed test program **cannot observe**, so I picked sane defaults rather than guessing at hidden C++ semantics:

- **Division by zero**: `fraction()` returns `0.0` when `total <= 0`. The real C++ may instead emit `inf`/`nan`/`-nan`. If you have a test that exercises an unset total, this is the first place it would diverge.
- **Default field values**: `ProgressBuilder` defaults to `total = 100`, `ProgressTracker` to `total = 0`. The test always sets both before reading, so these are unconstrained.

I also added `current_stage()`/`stages()` accessors so `add_stage` isn't write-only — the test registers three stages but never reads them back, so their intended semantics are unverified.
