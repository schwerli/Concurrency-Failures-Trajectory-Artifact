## What I did

The `indicators` header wasn't in the dataset (only `test20.cpp` + the binary), so this was genuinely black-box. I reverse-engineered the semantics from the 35 output lines by counting exact character runs:

| Inferred behavior | Evidence |
|---|---|
| Default bar width = **50** | `MultiProgress` bars: 15`=` + `>` + 34 spaces = 50 |
| `filled = width*cur/total`, then `>`, then padding | width 40→20`=`,25→8`=`,10→5`=`; interior always exactly `width` |
| `>` occupies an *unfilled* column | keeps interior width-stable; vanishes at 100% |
| Default precision = **1** | `Format::percentage(0.33)` → `33.0%` |
| `ProgressBuilder::build()` returns a **percentage string**, not a bar | line 8 is `50.0%` |
| Spinner = classic 8-frame braille cycle, index `current % 8` | `⣻` = U+28FB = frame 2 after two `next()` calls |

**The one real trap:** percentages must be computed in `f32`, not `f64`. C++ stored ratios in `float` and only widened at `operator<<`. `0.12345f * 100.0f` = `12.345000267…`, which prints `12.35` at two decimals — an `f64` computation gives `12.34` and silently fails that line. I confirmed Rust's `f32` arithmetic and `{:.*}` rounding match C++ exactly on all seven literals before writing the library. I also used integer arithmetic for `filled_cells`, since a float `width * ratio` can land at `8.2499994` instead of `8.25` and drop a tick.
