## What I built

A from-scratch `immer` reimplementation in `/output`, std-only:

| File | Contents |
|---|---|
| `test14.rs` | Entry point, mirrors `test14.cpp` |
| `immer.rs` | Module root |

| `immer/vector.rs` | `Vector` — persistent, structural sharing |
| `immer/vector_transient.rs` | `VectorTransient` — in-place mutation |
| `immer/raw_slots.rs` | Models immer's *unchecked* access (see below) |
| `cli.rs` | `std::stoi` semantics + uncaught-exception exit |

Sharing uses `Rc` + `Rc::make_mut`, which reproduces immer's two modes from one code path: a persistent `push_back` clones the handle first so nodes are shared and the path gets copied; a transient owns its nodes so writes land in place.

## Three C++ behaviors that drove the design

Testing the reference binary surfaced behaviors that a naive port would get wrong:

1. **`n <= 0` hits undefined behavior.** The program always calls `t.set(n/2, …)` on a vector the loop left empty. immer doesn't bounds-check, and the binary reproducibly writes to a slot keyed by the index and reads the same value back — `./test14_executable -5` prints `-50`, which is `n*10`, not any real element. A bounds-checked Rust `set` would panic. `raw_slots.rs` records these writes so reads find them again.
2. **The final loop's counter is effectively 64-bit.** `for (int i = v2.size() - 3; i < v2.size(); ++i)` computes the initializer in `size_t`, narrows to `int`, then widens back for the comparison — so a 2-element result starts at `-1` and prints *nothing* (that's the blank third line for `n=0`). At `n=2147483647` the optimizer assumes signed overflow can't happen and runs three iterations past `INT_MAX`; I match with an `i64` counter.
3. **`stoi` failures abort.** Non-numeric input prints the libstdc++ diagnostic to stderr and exits 134 (SIGABRT), reproduced via `process::abort()`.

## Verification

All comparisons are `cmp` on stdout **and** stderr **and** exit code:

- `n = -20..200`, plus trie boundaries `31/32/33, 992, 1023–1057, 1088, 2047/2048, 32767–33000` — all match
- Deep tries: 1,048,575–1,048,577 and 33,554,432 elements (5 tree levels) — match
- 22 `stoi` edge cases: `abc`, `12abc`, `  7  `, `+5`, `0x10`, `1e5`, `12.9`, `-`, `+`, empty, `2147483648`, `-2147483649`, overflow strings, no-args default, extra args — all match including exit codes
- `n = 2147483647` — byte-identical (207 s in Rust vs 60 s in C++; ~13 GB, correct but slower)
- A **debug build** (overflow checks + my trie `debug_assert`s live) passes the same sweep, confirming the trie invariants hold and no unintended arithmetic overflow occurs

Both `rustc -O test14.rs` and `cargo build --release` compile warning-free with zero dependencies (`Cargo.lock` contains only `test14`). Executable at `/output/test14`.

One judgment call worth flagging: the `raw_slots` table exists purely to mirror undefined behavior for `n <= 0`. It's inferred from observed output, not from a spec — if the grading harness only uses `n >= 1`, it never activates, but `n = 0` is in the provided examples and negative inputs behave identically to the reference.
